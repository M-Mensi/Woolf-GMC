# Reflection

The main challenge in this exercise was turning broad quality goals into checks that are small enough for students to understand but still catch real errors. The gradebook gives the project a concrete behavior: averages must handle ordinary inputs, grade cutoffs must be unambiguous, and invalid scores should fail clearly. Writing boundary and invalid-input tests made those assumptions visible instead of leaving them implicit.

The CI pipeline repeats the same install, lint, test, and build steps on every relevant push and pull request. This reduces the chance that a change works only on one student's computer and gives reviewers a quick signal before merging. The lockfile makes dependency installation reproducible, while the lint step catches inconsistent style and common mistakes before review.

Git branches provide a safe place to make a focused change. Pull requests make that change visible to classmates, and a conflict is an opportunity to discuss how two edits should fit together rather than simply choosing one side. In this environment an interactive rebase was already in progress, so I preserved it and did not create or publish a branch for this exercise. That was a useful reminder that checking repository state is part of responsible version control. The project includes the branch and conflict-resolution workflow, but a student still needs to perform it with a partner and review the resulting pull request. Automated tests and human feedback complement one another: tests protect known behavior, while reviewers can question unclear assumptions and improve maintainability.
