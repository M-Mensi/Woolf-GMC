# Reflection report

The hardest part of the refactor was avoiding a schema that looks scalable on paper but cannot serve the actual query patterns. A customer-hashed order key spreads ordinary checkout writes and targets a customer's history, yet one very large customer can still concentrate traffic. The revised time-bucket plus hashed-customer key adds a time boundary for retention and routing, but requires clients to include bucket values and makes cross-period history queries more involved. Search and transactional order writes also have different needs, so the catalog remains independently indexed instead of forcing every collection onto the same shard key.

Analytics changed the model more substantially than simply adding an index. Large historical aggregations would compete with checkout reads and writes, so the refactor records immutable per-order/product sales contributions and builds denormalized day/product/currency totals in bounded write buckets. This increases storage and introduces an asynchronous freshness window, replay, and reconciliation work. It was preferred to running repeated full scans over transactional orders. The report avoids claiming that a reservation of computing capacity guarantees a specific throughput; that must be benchmarked with realistic traffic.

Availability also required a consistency decision. Replicas and multiple shards provide redundancy and parallelism, while majority-acknowledged writes protect confirmed order changes. During a partition that prevents a voting majority, writes may fail or wait rather than be acknowledged without quorum. This favors consistent order state over uninterrupted checkout writes. The refactor improves horizontal distribution, resilience and dashboard query cost, but adds infrastructure cost, operational complexity and more difficult migrations. MongoDB Atlas Free can host the unsharded demonstration, not a sharded cluster, so the production topology cannot honestly be load-tested on that tier.
