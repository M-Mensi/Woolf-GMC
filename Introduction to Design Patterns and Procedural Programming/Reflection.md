# Reflection

The main challenge during the refactor was keeping the cart operations and their behavior the same while changing where the cart data lives. In the procedural version, the functions operate on a shared variable in the module. In the Module-pattern version, the items array is private inside a closure, and callers can use it only through the returned operations. I also had to keep the cart summary consistent, including quantity subtotals, the total, and TND formatting.

The Module pattern improves this small example by giving the cart a clear boundary. Other code cannot directly edit its item array, so all additions and removals pass through the same functions. This reduces accidental changes and keeps the global scope free of individual cart variables and functions. The module also exposes a compact API, which makes the implementation easier to replace or test. The trade-off is that the module represents one shared cart; it is not the right choice if an application needs multiple independent carts.

I would choose a design pattern when it solves a real organization or change-management problem, such as protecting shared state, creating multiple interchangeable implementations, or controlling a single shared instance. For a short script with a few operations and no shared state concerns, procedural code is often easier to understand and maintain. Patterns should clarify the design rather than add structure without a practical benefit. Here, the Module pattern is useful as a demonstration of encapsulation, while the procedural version remains the most direct solution for the stated cart behavior.
